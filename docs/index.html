EMCCD photon counting toolkit

Bin a night, keep the physics

Turn a folder of raw PESTO frames into a flux map and light curves, keeping 16 numbers per pixel instead of one number per pixel per frame, and losing 0.6 % of the precision doing it.

What this toolkit is, in one screen

There are two programs and one settings file. You edit the settings file. You do not edit the programs.

your frames → per-pixel histogram → flux map → stars → light curves

An EMCCD read is not "the flux, plus a bit of noise". A pixel that collected n photo-electrons during one frame reads out at

bias + Gamma(n, gain) + Gaussian(0, read noise)

The electron-multiplying register multiplies each electron by a random amount, so the same n gives wildly different ADU values from one frame to the next. Averaging the ADU values throws away most of the information at the sub-electron fluxes these cameras are used at. What carries the flux is the shape of each pixel's distribution of ADU values, and that shape is what a histogram keeps.

So for every pixel this toolkit counts how many frames had that pixel between 0 and 314 ADU, how many between 314 and 321, and so on through 16 bins. Then it asks, pixel by pixel, which mean flux makes those 16 counts most likely. That fitted flux, in electrons per frame, is the output.

Where the 16 boundaries come from. They are not round numbers picked by hand. They are computed, for this camera, to lose as little information as a 16-bin histogram possibly can: page 3 explains how, and what it costs.

The files you will touch

File What it is
embin_config.yaml The only file you edit. Every setting, explained line by line inside the file itself.
run_chunks.py The program you normally run: a whole sequence, cut into chunks of frames.
embin.py One set of frames → one histogram cube and one flux map. Used by the program above, and usable on its own.
plot_bins.py Draws your bin edges on top of your own data, so you can see they land where the counts are.
bin_optimizer.py Computes bin edges for a camera. Run it once per detector or gain setting.
data_bin/ Where every result is written. Created for you.

Installing it, once

You need Python 3.9 or newer. Open a terminal and run these four commands, in order. Each one is explained, because skipping the reason is how people end up stuck.

1 Get the code

git clone https://github.com/eartigau/emccd_bintool.git cd emccd_bintool

2 Make a virtual environment

A virtual environment is a private copy of Python for this project. It means the packages you install here cannot break anything else on your machine. The command creates a folder called .venv inside emccd_bintool.

python3 -m venv .venv

3 Activate it

You must do this every time you open a new terminal to work on this project. You know it worked when your prompt starts with (.venv). Nearly every "it says numpy is not installed" message comes from having skipped this step in a fresh terminal.

source .venv/bin/activate # macOS and Linux .venv\Scripts\activate # Windows PowerShell

4 Install the packages

pip install -r requirements.txt

5 Check it works

python bin_optimizer.py --bias 303.6178 --gain 71.0598 --ron 6.8164 --sat 5000 \ --nbins 16 --mu-min 1e-3 --mu-max 4

You should get a table of 16 bins and a line saying the worst-case efficiency is about 0.989. If you get ModuleNotFoundError instead, step 3 or 4 did not happen.

Running it on a night of data

1 Put your frames in data_night

One FITS file per readout, which is how PESTO writes them: nc-image_0.fits, nc-image_1.fits, and so on.

mkdir data_night cp /wherever/your/frames/are/*.fits data_night/

If the frames are big and you would rather not copy them, open embin_config.yaml and point input.directory at where they already live instead.

2 Look at where your bins land

python plot_bins.py

This writes data_bin/figures/bins_on_data.pdf. Open it. You should see a tall narrow peak (the read noise, where most pixels sit because most pixels see no electron at all in a given frame), a long tail to the right (the amplified electrons), several bin edges cutting through the peak, and the last edge sitting where the tail has died out. If your edges are instead floating in an empty region, the detector constants do not match this data and everything downstream will be wrong. Stop and fix that first.

3 Try two chunks before the whole night

python run_chunks.py --n-chunks 2

About 30 seconds per chunk. The program narrates what it is doing in colour: green for progress, blue for a measured number, orange for something it skipped, red if it is stopping. Read it, and check three things: it found your frames, the sky level it reports is sensible (0.016 e-/frame on the PESTO test sequence), and it found some stars.

4 Run the whole thing

python run_chunks.py

On the 1001-frame PESTO test sequence this takes about 3.5 minutes and produces 15 chunks. Everything lands in data_bin/. Page 2 says what each file contains and how to open it.

Why the night is cut into chunks

A histogram is built per pixel. It only means something if the star stayed on that pixel for the whole set of frames.

Real fields drift. On the PESTO test sequence the field moves about 0.16 pixel per second, so over the full 1000 frames (49 seconds) it moves 7 pixels. A histogram of the whole night would smear every star across 7 pixels and tell you nothing about any of them. That is why the sequence is cut into consecutive chunks of chunks.size frames, each analysed on its own.

Choosing the chunk size is the usual exposure-time trade-off wearing a new hat:

  • More frames per chunk: more reads per pixel, so a more precise flux, but the star drifts further during the chunk and smears.
  • Fewer frames per chunk: the star stays put, but each flux is noisier.

64 frames on this sequence is 3.1 seconds and about half a pixel of drift, which is a good compromise. Frames left over at the end are dropped, and the program tells you how many: with 1001 frames and chunks of 64 you get 15 chunks using 960 frames, and 41 frames are dropped.
